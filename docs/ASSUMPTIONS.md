# ASSUMPTIONS

- Registry: GHCR `ghcr.io/<owner-lower>/payment-api:<sha>` (+worker/mock-provider); локально `northwind/payment-*:<version>`. Версия: `APP_VERSION` → git SHA → `VERSION` (ZIP без `.git`) → `nogit-<UTC>`; `package.sh` кладёт сгенерированный `VERSION` в ZIP. `deploy.sh` по умолчанию собирает локально; pull из GHCR — отдельным шагом (разрыв зафиксирован, не скрываем).
- Vault dev-режим достаточен для стенда; прод-Vault (HA/Raft) — за рамками, но интерфейс `seed [--force] → render --strict` сохранится.
- `003_add_amount_minor` уже применена везде — считаем базовым состоянием, но признаем: `DROP COLUMN amount` был не expand/contract и необратим. Новые миграции только backward-compatible.
- `client_ip` храним в БД, но наружу по API не отдаем (PII-риск: без auth любой мог читать чужое через `GET /transfers/{id}`). Важно: сейчас это IP reverse-proxy, а не клиента — nginx не прокидывает `X-Real-IP`, API читает `request.client.host`; исправление отложено (см. LIMITS). Маскирование вместо чистки — совместимость тестов/consumer сохранена.
- Сеть по умолчанию bridge от compose; TLS на входе (443) не делаем — за proxy выше по уровню. Наружу из base — только proxy `${API_PORT}:80`; debug-порты только в stage на loopback. Stage/prod — отдельные compose-проекты `payment-stack-<env>`, отдельные `runtime.<env>.env` и `backups/<env>/`; на одном хосте они не пересекаются. Для старого стенда с проектом `deploy` предусмотрен явный override `PAYMENT_STACK_PROJECT=deploy PAYMENT_STACK_RUNTIME_ENV=runtime.env`.
- `POST /transfers` требует `Idempotency-Key` по умолчанию (`REQUIRE_IDEMPOTENCY_KEY=true`); `false` оставлен только для legacy-клиентов и снимает защиту от дублей. Один ключ = один transfer; повтор с тем же телом → 200, с другим → 409. Outbox гарантирует доставку принятого перевода до RabbitMQ, но не заменяет клиентскую идемпотентность.
- `outbox` — отдельный контейнер на образе worker; `transfer_outbox` хранит `PENDING/SENT`, ретраи с backoff, `SENT` не удаляются автоматически. Если outbox лежит, API принимает переводы, а доставка ждёт восстановления.
- Deploy/rollback/rotate/restore сериализованы `flock`; deploy собирает только чистый git tree (`ALLOW_DIRTY=1` — явный обход для отладки). Pre-migration backup обязателен; мигратор ждёт advisory lock до 30s, падает по таймауту и проверяет checksums уже применённых миграций.
- Alertmanager доставляет в локальный `alert-sink` (webhook); `Watchdog` всегда горит как dead man's switch, а `alert-selftest` дополнительно шлёт уникальный синтетический `SelfTest` через Alertmanager API. Это проверка цепочки, а не внешний pager. Внешний канал заменяется URL в `monitoring/alertmanager.yml`; `AlertSinkDown` ловит падение sink.
- CD deploy предполагает self-hosted runners с labels `stage`/`prod`, persistent checkout path (`STAGE_DEPLOY_PATH`/`PROD_DEPLOY_PATH`) и Docker/make/Git. Repository variables `*_DEPLOY_ENABLED` включают job'ы; prod требует environment approval. Deploy идёт из clean checkout того же SHA, что собран/просканирован; registry digest как источник деплоя не используется.
- `mock-provider` — stand-in внешнего провайдера; контракт `POST /payouts → {payout_id,status}` достаточен. Идемпотентность по `Idempotency-Key` только в памяти: рестарт мока сбрасывает `state.payouts`, повтор даст новый `payout_id` (для мока ок, в проде так нельзя). `/admin/fail-mode` закрыт ключом `X-Api-Key/X-Admin-Key = PROVIDER_API_KEY`.
- `seed.sh` без `--force` идемпотентен (не затирает ключ); ротация DB/Rabbit-паролей — только `rotate.sh` (ALTER + rabbitmqctl + seed), `seed --force` — только если пароли БД/очереди не меняются. `--strict` в `render-env.sh` отбрасывает слабые плейсхолдеры; `runtime.<env>.env` пишется с правами 0600.
- Чистая машина по заданию = Docker Compose v2 + Git + make + интернет; фактически deploy-скрипты также требуют `bash` и `flock` из util-linux (стандартные пакеты на типичном Linux-хосте, но их нужно доустановить на минимальном). `curl`/`python3` на хосте опциональны: host-smoke требует оба, без любого из них `deploy.sh`/`rollback.sh`/`restore.sh` переключаются на in-network `smoke-net.sh` (python внутри контейнера). `openssl` тоже опционален: генерация секретов fallback `openssl → python3 → /dev/urandom`.
- Бэкапы лежат в `backups/<env>/`, checksum обязателен для restore; `--apply` по умолчанию сначала верифицирует дамп в temp DB и делает safety-backup. Это удваивает место/время restore, зато битый дамп не доходит до live БД.
- Сумма перевода ограничена `MAX_AMOUNT_MINOR = 10^12` (10 млрд единиц валюты); выше — 400, а не 500/BIGINT-переполнение. Форматирование сумм для API/провайдера — целочисленное (`minor // 100` + `minor % 100`), без float.
- Vault-токен стабилен per-env: env-токен записывается в `.vault-token-<env>`, а расхождение с сохранённым — FATAL. README-блок `gen` предназначен только для первого запуска; повторная генерация DB/Rabbit-паролей запрещена, для смены — `rotate.sh`.
- `deploy-smoke` на `ubuntu-latest` — доказательство чистого деплоя HEAD; реальные stage/prod остаются на self-hosted runners и включаются repository variables.
